# 07 — API Reference

> **338 HTTP endpoints under `/api`.** This doc is the canonical
> reference. It was generated by scanning every
> `router.<method>('<path>')` in `Backend/src/routes/`; the source
> code is the source of truth if anything here disagrees.

> For the data flow, see
> **[02 — Architecture §2.2](./02-ARCHITECTURE.md#22-request-lifecycle--read-path)**.
> For the env vars that control these endpoints, see
> **[08 — Configuration](./08-CONFIGURATION.md)**.

## 7.1 Conventions

- **Path**: all endpoints are mounted at `/api/*`. When the path in
  the table says `/auth/heartbeat`, the full path is
  `GET /api/auth/heartbeat`.
- **Auth**: every endpoint except the public allowlist
  (`/api/captcha`, `/api/auth/captcha`, `/api/login`,
  `/api/auth/login`, `/api/forgot`, `/api/auth/forgot`,
  `/api/dev/login`, `/api/auth/dev-login`, `/api/heartbeat`,
  `/api/auth/heartbeat`, `/api/live`, `/api/ready`, `/api/health`,
  `/api/metrics`) requires a valid session cookie. A 401 with code
  `SESSION_EXPIRED` or `UNAUTHORIZED` triggers the SPA to redirect
  to `/login`.
- **Body shape**: request and response are JSON unless otherwise
  noted. The `Content-Type: application/json` header is required on
  any non-GET request with a body.
- **Error envelope**: every non-2xx response is structured:
  ```json
  {
    "success": false,
    "error": {
      "code": "ERROR_CODE",
      "message": "Human-readable message",
      "retryable": false
    },
    "requestId": "<uuid>"
  }
  ```
- **Success envelope** for mutations: `{ success: true, data: ... }`.
  For list reads, the data is at the top level
  (e.g. `{ events: [...], total: 42 }`).
- **CORS**: same-origin lockdown by default; `CORS_ALLOWED_ORIGINS`
  is the explicit opt-in for cross-origin.

## 7.2 Path parameters

The API uses these conventions:

- `:id` — opaque string ID (event, ticket, opportunity, ...)
- `:eventId` / `:userId` / `:teamId` / etc. — typed ID (the system
  keeps register numbers in plain text; other IDs are UUIDs)
- `:pageKey` / `:category` / `:page` — ERP-style slugs
  (e.g. `academic/attendance-details`, `Academic`, `Attendance Details`)
- `:roundId`, `:submissionId`, `:invitationId`, etc. — typed ERP
  sub-IDs

## 7.4 WebSocket / SSE

The platform does not use WebSockets or Server-Sent Events. All
data is poll-based (the SPA re-fetches every page load, the React
Query cache has a 30s stale time, and the backend has a 60s fresh
cache TTL for ERP pages). Background jobs (competition reminders,
career notifications, etc.) are polled, not pushed.

## 7.5 Rate limits

- **Global**: 400 requests/min/IP (configurable via `RATE_LIMIT_MAX`).
  Applied to all `/api/*` after CORS + helmet + cookieParser.
- **Login**: 20 requests/min/IP for the auth allowlist
  (`/api/captcha`, `/api/login`, `/api/forgot`).
- **No per-endpoint limits** other than the global. The career
  scraper-trigger endpoint is admin-gated but not separately
  rate-limited.

429 responses include a `Retry-After` header (in seconds) and the
standard error envelope with `code: "RATE_LIMITED"`.

## 7.6 Deprecation policy

The platform doesn't have a formal API deprecation policy yet. The
recommended pattern is:

1. Add a new endpoint under a versioned path (`/v2/erp/batch` →
  next iteration becomes `/v3/erp/batch`)
2. Mark the old endpoint with `Sunset: <date>` and `Deprecation:
  <reason>` response headers
3. Keep the old endpoint working for at least one academic year
4. Once the new endpoint is stable, update the SPA to use the new
  one and remove the old endpoint

The V2 ERP endpoints (`/v2/erp/*`) are the first instance of this
pattern in action.
