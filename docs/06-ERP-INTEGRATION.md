# 06 — ERP Integration

> How the platform talks to the legacy SRM AP University ERP
> (`student.srmap.edu.in`). The ERP is a traditional JSP/HTML app with
> no API, so the platform scrapes each page with Playwright (or the
> Playwright `request` API for non-JS pages), parses the HTML with
> Cheerio, validates the result against a per-page contract, and
> serves a typed JSON payload to the SPA. This doc walks the full
> pipeline: discovery → scrape → extract → validate → cache → serve.

For data flow and the request lifecycle, see
**[02 — Architecture §2.4](./02-ARCHITECTURE.md#24-the-erp-scrape-pipeline)**.
For the data layer (cache, circuit, etc.), see
**[05 — Data §5.2](./05-DATA.md#52-redis-namespaces)**.

## 6.1 Why this exists

The upstream ERP exposes no API. Every page is rendered server-side
from a JSP template. The platform turns each of those pages into a
JSON endpoint the SPA can consume. Three principles:

1. **The frontend never talks to the ERP directly.** All scraping
   goes through the backend.
2. **Schema-driven rendering.** ERP pages are not hand-written
   per page in the SPA; the SPA's `ErpPage` generic component
   reads the typed payload and dispatches to the right renderer.
3. **Pipeline-guarded data.** Every scraped payload passes
   extract → validate → cache. A page that can't be parsed correctly
   is treated as a 5xx, not a silent `[object Object]`.

## 6.3 Discovery (one-time)

The first time you deploy, you run:

```bash
cd Backend && npm run discover:endpoints
```

This walks the live ERP's navigation, captures the URL + payload of
each reachable page, and writes `Backend/data/endpoint-discovery.json`.
The output is a flat list of `(category, page, url, method, payload-shape)`
triples. It's checked in to the repo (the `!Backend/data/*.json` rule
in `.gitignore` is for the `live-page-audit` output, not the
discovery file).

From the discovery output, two config files are generated:

- **`Backend/src/config/scrapeTargets.js`** — maps each `pageKey` (the
  URL slug, e.g. `academic/attendance-details`) to the dropdown +
  subitem that the ERP menu uses to navigate to that page
  (e.g. `{dropdown: "Academic", subitem: "Attendance Details"}`).
- **`Backend/src/config/erp-page-policy.json`** — for each `pageKey`,
  whether to serve `cached-first` or `live-first`. Generated by
  classifying pages into "rarely changes" (cached-first) and
  "user-action triggered" (live-first).

Both files are checked in and updated by hand when pages are added.
See **[12 — Contributing](./12-CONTRIBUTING.md)** for the workflow.

## 6.4 Scrape (per request)

`Backend/src/services/erp/erpClient.js` is the live-scrape layer.
Two modes:

- **`request` mode** — uses Playwright's HTTP client (no browser
  binary). Used for pages that don't need JS to render. Most ERP
  pages fall in this category.
- **`browser` mode** — uses Playwright with Chromium. Used for
  pages that need JS to render. Currently only the login page
  (which has a JS-based captcha) uses this.

The client maintains a per-user session (cached JSESSIONID) so each
request reuses the same authentication.

### 6.4.1 The login flow

The full login lifecycle:

1. SPA calls `GET /api/captcha` → backend's `authRoutes` handler
   generates a captcha (PNG image + session-bound answer key, 25-min
   TTL on the pre-auth session).
2. User submits captcha text + register number + password to
   `POST /api/auth/login`.
3. Backend's `authRoutes` handler:
   - Validates the captcha against the pre-auth session
   - Reuses or creates a Playwright browser context
   - Loads `StudentLoginPage`, fills in reg-no + password + captcha
   - Submits, waits for the post-login redirect
   - Stores the resulting JSESSIONID + cookies in the user's session
   - Captures the post-login profile for the cache
4. SPA is now logged in. Subsequent requests use the same JSESSIONID.

Login failures and timeouts are stored in
`Backend/logs/login-attempts/` (capped at 20 files, redacted) for
post-incident analysis.

### 6.4.2 The per-page fetch

Once the user is logged in, each ERP page fetch follows the same
pattern:

```
async function fetchErpPage(userContext, pageKey) {
  // 1. Resolve the (dropdown, subitem) for this pageKey
  const targets = scrapeTargets[pageKey];

  // 2. For each (dropdown, subitem), navigate to it and capture the
  //    POST response (the ERP uses POST to fetch each sub-page)
  const htmls = await Promise.all(
    targets.map(({ dropdown, subitem }) =>
      erpClient.fetchSubPage(userContext.session, dropdown, subitem)
    )
  );

  return htmls;
}
```

The ERP uses a `<form action="..." method="POST">` pattern to fetch
each sub-page; the client mimics this with a `request.post()` call.

## 6.5 Extract (per request)

Each `pageKey` has a targeted extractor — a small Cheerio-based
function that takes the raw HTML and returns a typed payload.

`Backend/src/services/erp/extractors/index.js` is the registry:

```js
const SUBITEM_EXTRACTORS = {
  "Academic|Attendance Details": extractAttendance,
  "Academic|Time Table": extractTimetable,
  "Examination|Current Semester Results": extractCurrentResults,
  "Finance|Fee Due Details": extractFeeDues,
  // ... 40+ entries
};
```

The key is `<dropdown>|<subitem>`. For example, the
`Academic|Attendance Details` extractor parses the
`tblSubjectWiseAttendance` table into:

```ts
type AttendanceRecord = {
  subjectCode: string;
  subjectDescription: string;
  classesConducted: number;
  present: number;
  absent: number;
  odMlTaken: number;
  presentPercentage: number;
  odMlPercentage: number;
  attendancePercentage: number;
};

type AttendanceData = {
  type: "attendance";
  title: string;
  period: string;  // "From 2024-01-01 To 2024-06-30"
  records: AttendanceRecord[];
};
```

The 20 targeted extractors are:

| File | What it parses |
|------|----------------|
| `extractAnnouncements.js` | The announcements list |
| `extractAttendance.js` | Subject-wise attendance grid |
| `extractBankDetails.js` | Bank account info (labels + values) |
| `extractCurrentResults.js` | Current-semester results |
| `extractEarlierInternalMarks.js` | Earlier-internal-marks parent (lists semesters) |
| `extractEarlierInternalMarksSemester.js` | Earlier-internal-marks per-semester detail |

### 6.5.1 The legacy-payload adapter

The targeted extractors return **typed** data. The rest of the
system (caching, validation, frontend renderers) was originally
written for the legacy shape:

```js
{
  title: string,
  text: string,
  tables: Array<Array<Record<string, string>>>,
  meta: { ... }
}
```

To avoid breaking the rest of the pipeline, the extractor registry
includes an `adaptToLegacyPayload(extracted)` function that wraps the
typed result in the legacy shape. The typed result is also embedded
under `._extracted` for frontends that can consume it directly.

## 6.6 Validate (per request)

`Backend/src/config/erpPayloadContracts.js` defines per-page
contracts:

- `TABLE_REQUIRED_PAGE_KEYS` — pages that MUST have at least one
  table (the catchall "no data yet" page is rejected)
- `MEANINGFUL_TEXT_FALLBACK_PAGE_KEYS` — pages where a non-empty
  `text` summary is enough (e.g. announcements)
- `defaultContract` — `{ kind: "default", requireTargetSections: true,
  rejectSuspiciousText: true, minTableCount: 0,
  allowMeaningfulTextFallback: false }`
- Per-page overrides via the `getPayloadContract(pageKey)` function

The `validateLivePayload(pageKey, payload)` function checks:

1. Does the payload have at least the required number of tables?
2. Does the text contain "suspicious" markers (e.g. "access denied",
   "session expired", empty content where there should be data)?
3. Is the typed extraction present (i.e. did a targeted extractor
   run, or did the system fall back to the generic pipeline)?

A failed validation throws a `PayloadContractError` (HTTP 502 with
code `ERP_PAYLOAD_CONTRACT_VIOLATION`).

## 6.7 Cache (per request)

The aggregation service owns the cache. See
**[02 — Architecture §2.5](./02-ARCHITECTURE.md#25-caching-strategy)**
for the full lifecycle.

Two TTLs:
- **Fresh** (default 60s) — returned immediately, no background
  refresh
- **Stale** (default 600s) — returned with `source: "cache-stale"` +
  a background refresh is fired

Per-page policy (`erp-page-policy.json`):
- **Cached-first** (default): dashboard, attendance, timetable,
  results, exam marks, fee dues
- **Live-first**: fee paid, payment acknowledgments, exam registration,
  course registration

Override the policy per-request with `?mode=live` or `?mode=cached`.

## 6.8 Circuit breaker (per pageKey)

A per-pageKey failure counter in Redis. If 5 failures happen in a
sliding window, the circuit opens for 30s and live scrapes return
`503 UPSTREAM_UNAVAILABLE` (or fall back to the offline dump if one
exists).

The circuit is reset on the next successful scrape.

## 6.9 Distributed lock (per user per pageKey)

A Redis `SETNX` lock with a 12s TTL. If two backend processes (or
two requests from the same user) try to scrape the same page at the
same time, only one succeeds; the other waits for the first to
finish (or returns stale cache).

This prevents the "thundering herd" problem when a page is requested
by a user and the cache has just expired.

## 6.10 The frontend side (SPA)

The SPA has its own ERP integration layer in
`Frontend/src/lib/erp/`:

- **`erpTransformers.ts`** — the registry of per-page transformers
  (e.g. `transformAttendance`, `transformTimetable`) that take the
  typed backend payload and produce a domain model the SPA can render
- **`schemas.ts`** — Zod (or similar) schemas for runtime validation
- **`api.ts`** — the typed client for `/api/erp/batch?keys=...` and
  `/api/scrape/:pageKey`
- **`queryKeys.ts`** — React Query key factory
- **`registry.ts`** — maps each `pageKey` to a transformer + schema

The flow on the frontend:

1. Page calls `useQuery({ queryKey: erpKeys.batch([...fetchKeys]),
   queryFn: () => erpApi.batch(fetchKeys) })`
2. Backend responds with `{ success, source, fetchedAt, staleAt,
   policyMode, data: { [pageKey]: payload, ... }, meta, warnings }`
3. Per-page React component takes the typed payload and renders it
4. If the payload is `null` or the typed extraction is missing, the
   renderer shows a fallback ("No data yet" or an error message)

### 6.10.1 The renderers (`src/components/erp/`)

Generic renderers that the SPA's `<ErpPage>` dispatches to based on
the blueprint:

- `<TableRenderer>` — renders a list of records as a table
- `<CardGridRenderer>` — renders a list of cards
- `<KpiRenderer>` — renders a set of KPI tiles
- `<CalendarRenderer>` — renders a date-aware grid (timetable, etc.)
- `<GenericRenderer>` — fallback for any page

Each renderer takes the typed payload and a schema; it doesn't need
to know which pageKey produced the payload.

## 6.11 Offline dump (fallback)

`Backend/src/services/erp/erpServices.js#resolveLatest()` returns
the most recent snapshot in `Backend/data/erp-dump/`. The format is
a directory of per-pageKey JSON files. The snapshot tool is
`Backend/scripts/create-erp-dump.js` (run with `npm run dump:erp`).

The dump is treated as a hard floor — once a user sees data, that
data doesn't change shape between live and dump. The dump is used
when both the cache miss and the live scrape fail (e.g. the
upstream ERP is down).

## 6.12 The V2 surface

`Backend/src/routes/erpV2Routes.js` adds typed output, schema
validation, and a different request shape (one batch call instead
of N page calls). The V2 surface is feature-gated by
`FEATURE_ERP_V2_API` and used by the newer SPA pages.

The V2 request:

```http
POST /api/v2/erp/batch
Content-Type: application/json
{
  "pageKeys": ["dashboard", "academic/attendance-details"],
  "mode": "cached-first" | "live-first"
}
```

The V2 response uses the same shape as V1 (`{ success, source, data,
meta, warnings }`) but `data` is keyed by `pageKey` and each entry
has been through `validateExtractedTargetSections` and a
`dataSink`-typed projection.

## 6.13 The scraper supervisor (career)

The career scraper is a separate process — a Python script in
`Scraper/main.py` that's run by the `careerScraperSupervisor` in
`Backend/src/services/career/careerScraperSupervisor.js`. The
supervisor:

- Starts the Python script as a child process
- Restarts it on crash with backoff 30s → 15min
- Exposes its state via `GET /api/career/health` (the SPA's
  "is the scraper alive" probe)
- Reads the state from the `career-scraper-health.json` file the
  Python script writes

The Python scraper is documented in its own README
(`Scraper/README.md`) and is not in the ERP integration critical path
(it's a parallel data-source, not the primary one).

## 6.14 When the upstream ERP changes

The most common breakage mode is a structural HTML change in the
upstream ERP — the extractor expects a particular selector and the
ERP renders a slightly different structure. The
**end-semester-tests for this are not yet automated**; the discovery
flow + the 7-12 test suite is the current mitigation.

The recovery playbook:

1. Run `npm run discover:endpoints` to capture the new HTML
   structure
2. Run `npm run audit:live-pages` to see which pages now fail
   validation
3. For each failing page, update the targeted extractor
   (e.g. `extractAttendance.js`) to match the new structure
4. Run the unit tests for that extractor
5. Re-run the discovery to update `scrapeTargets.js`
6. Commit, push, deploy

If a page has no targeted extractor, it falls back to
`extractGenericTable` which only requires a `<table>` with a
specific expected `<title>`. The page can degrade gracefully until
a targeted extractor is added.

## 6.15 Performance budget

The full pipeline has the following latency budgets (per request):

| Stage | Budget | Notes |
|-------|--------|-------|
| Cache lookup | < 5ms | Redis GET |
| Cache miss + distributed lock | < 50ms | Redis SETNX |
| Live scrape (request mode) | < 1.5s | Playwright `request.post` |
| Live scrape (browser mode) | < 3s | Playwright Chromium |
| Extract | < 50ms | Cheerio parse |
| Validate | < 10ms | Per-page contract check |
| Cache write | < 5ms | Redis SET |
| **Total (cache hit)** | **< 20ms** | dominant: cache lookup + JSON serialize |
| **Total (cache miss, live)** | **< 2s** | dominant: live scrape |
| **Total (cache miss, browser)** | **< 3.5s** | dominant: browser roundtrip |

The whole pipeline is bounded by the `ERP_CACHED_TIMEOUT_MS` (6s
default) and `ERP_LIVE_TIMEOUT_MS` (15s default). If the live
scrape exceeds the timeout, the system returns whatever it has
(cache, dump, or a partial payload with a warning).

## 6.16 Failure modes and recovery

| Failure | Behavior |
|---------|----------|
| Redis down | In-memory fallback for sessions + rate limits. Cache and circuit use per-process in-memory (only useful in single-process setups; multi-process would have inconsistent cache and circuit state). |
| Live ERP down (timeout, 5xx) | Return the cache if fresh or stale; if both, return the offline dump if one exists; if not, return 503 with `UPSTREAM_UNAVAILABLE` |
| Captcha incorrect | 401 `INVALID_CAPTCHA` |
| Session expired | 401 `SESSION_EXPIRED`; SPA redirects to `/login` |
| Discovery JSON missing | 503 with `DISCOVERY_MISSING` |
| Circuit open | 503 with `CIRCUIT_OPEN` (and the cache, if any) |
| Payload fails contract | 502 with `ERP_PAYLOAD_CONTRACT_VIOLATION` (the response includes the warnings; the SPA shows a "data may be incomplete" banner) |
| Lock contention | Wait up to 1.5s for the holder to finish; if it doesn't, fall back to the cache or the dump |
